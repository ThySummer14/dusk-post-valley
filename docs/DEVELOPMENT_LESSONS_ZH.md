# 《暮邮谷》开发复盘：让一条像素邮路看得清，也走得通

记录于 2026-10-08，对应游戏 **v0.3-r1**。这是一个仍在打磨的 Godot 4.6.3 原型：雨后山谷、三封来信、一盏灯和一面旧镜。本文记录已经遇到、修过并检查过的问题，也保留尚未验证的部分。

[打开试玩](https://thysummer14.github.io/dusk-post-valley/) · [返回项目首页](../README.md) · [运行测试](../TESTING.md)

## 参考了什么，怎么变成自己的东西

Graytail、REPLACED、《雨世界》和《星露谷物语》来自项目发起者给出的艺术方向与偏好参考，帮助讨论像素场景、氛围和观看角度。这里没有把它们写成逐部视频分析，也没有声称研究过它们的内部渲染实现。游戏的人物、邮路故事、几何场景和程序材质独立制作。

实际用于技术核查的是 Godot 官方的 [SubViewport](https://docs.godotengine.org/en/4.6/classes/class_subviewport.html)、[多分辨率](https://docs.godotengine.org/en/4.6/tutorials/rendering/multiple_resolutions.html)、[灯光与阴影](https://docs.godotengine.org/en/4.6/tutorials/3d/lights_and_shadows.html)及[渲染器说明](https://docs.godotengine.org/en/4.6/tutorials/rendering/renderers.html)。另读了 Minecraft 光影包 Complementary Reimagined 的 [合成阶段](https://github.com/ComplementaryDevelopment/ComplementaryReimagined/blob/main/shaders/program/composite.glsl)、[雾](https://github.com/ComplementaryDevelopment/ComplementaryReimagined/blob/main/shaders/lib/atmospherics/fog/mainFog.glsl)和[反射模块](https://github.com/ComplementaryDevelopment/ComplementaryReimagined/blob/main/shaders/lib/materials/materialMethods/reflections.glsl)，观察它怎样拆分光色、距离层次和反射成本。

有用的收获是组织方法：先分清环境光、主光和局部光的职责，再调水、雾和高光。Minecraft 光影依赖自己的深度、法线、材质编号及渲染阶段，无法直接粘进 Godot。本项目没有复制或移植它的 shader；它的[许可证](https://github.com/ComplementaryDevelopment/ComplementaryReimagined/blob/main/License.txt)也不能被“仓库公开”四个字替代。

## 1. 像素感要从相机和构图开始

这里选用固定斜俯视的正交 3D 相机。正交意味着远处的物体不会因为透视而明显缩小，便于安排房屋、树冠和路面的色块。世界先画进低分辨率 SubViewport，再以最近邻方式放大；16:9 的基线是 480×270，其他比例另行适配。文字、按钮和信件在根视口绘制，保持清楚。

第一轮实图仍像“低模场景缩小”：草地棋盘过于整齐，圆锥树重复排列，地图断面像悬空切块。仅降低分辨率没有解决构图。后来改为不对称的分层树冠，分别安排路缘草、树下暗土、河边碎石与芦苇，并用远景谷壁弱化边界。细节围绕路径和生活区域分布，空地保留呼吸感。

相机对齐也有一个容易踩的坑：斜相机的屏幕水平、垂直方向并不是世界 X、Z 轴。相机位置应先投影到自己的 right/up 方向，再按一个世界像素对应的距离取整。相关实现集中在 [main.gd](../game/scripts/main.gd) 的 `_setup_world`、`_resize_world` 和 `_update_camera`。数学对齐可以减少不稳定，但不能替代移动录像中的边缘观察。

## 2. 夜色靠局部明暗，灯亮还要照到人

早期路面发白、阴影不自然，部分地面法线方向也有问题。法线可以理解为告诉光照“这个面朝哪里”的箭头；箭头错了，再调曝光也救不回来。修正网格绕序与朝上法线后，才分别调整太阳、环境光和阴影偏移，并用同机位画面比较，避免凭记忆把全场越调越暗。

另一张夜图暴露了更直接的问题：窗很亮，门前地面和角色却没有得到暖光。自发光材质能让窗自己显亮，当前方案下不会自动照亮邻居。于是给门前增加小范围真实 OmniLight3D，并配合一小块柔和的地面光斑。冷色环境托住暗部，暖色集中在入口、灯旁和可交互位置，夜晚依然保留大片较暗空间。

v0.3 又发现路灯“照亮地面，却看不见灯芯”。原因是实心灯罩把较小的发光片完整包住了。修法是改成顶盖、底座和四根细框，让灯芯露出来。这是几何遮挡问题，提高亮度只会掩盖原因。

当前主要成本是一盏投影主灯和有限范围、无阴影的局部灯。水面使用原创波纹和随观看角度变化的天空色混合，属于风格化反射；没有实现实时场景镜像、SSR 或体积光。后续应测真实设备的灯光重叠开销，不能凭低分辨率推断一定流畅。

## 3. 谜题答错时，也要有东西可看

旧镜子原先只有转对后才显示有用光路。朝错方向时，提示说光会指路，画面却没有反馈，玩家无法知道自己改变了什么。

现在点灯后，入射光、反射光和落地光斑会跟随四个镜面朝向变化。光束用少量原创网格表现，光斑附近有一盏小范围实际灯。它是四向玩法近似，没有宣称物理光线追踪。修正过程中还发现镜面旋转符号与方向文字不一致，一并对齐。

状态必须分清：**信件已经被发现**是历史进度，**镜子当前照向哪里**是当前画面。解谜后再次转镜，光束仍应转动，已发现的信不能凭空消失。先转镜再点灯、先点灯再转镜，都需要得到一致且只出现一次的发现确认。实现见 [world_builder.gd](../game/scripts/world_builder.gd) 的 `_update_beam`，规则见 [quest_state.gd](../game/scripts/quest_state.gd)。

## 4. 画出来的路必须真的能走

第三封路线的实测发现，前两封送完时玩家常在东岸，而镜子在西岸。只写“去找旧镜”没有告诉人该怎样回去。目标现在会按所在岸侧提示木桥与西岸石径，镜座与桥头之间也补上可见的小路。

更严重的是东岸一段石路穿过房屋碰撞范围，末端又指向屋内。寻路系统即使能找到另一条路线，也无法替这条误导人的美术路径辩护。修正后的路绕过房屋占地，直达观星屋门，两块小紫布呼应屋顶颜色。测试逐段采样路面，检查实际通行空间，而不只检查起终点能否连通。

第三封的过桥、点灯、转镜、拾取、回东岸和门前送达，已分段用实际键鼠检查。中途失焦暂停后，最后门前一步通过保留拾信进度的检查点续测完成。因此证据支持“各段与交互可完成”，还不能写成“一次无中断盲玩通关”。

## 5. UI 裁切是真问题，旧截图不一定是输入问题

开场正文曾被截掉半行。原先按字符数估高度，不足以代表中文实际换行。修法是按字体排版结果计算高度、缩短开场文字，长内容允许滚动，关闭按钮留在固定位置。送达后增加收件人姓名与短暂回执；弹窗打开时隐藏旧世界交互提示，关闭后按新进度重算，避免刚送完又显示“敲门送信”。

输入检查则提醒我们不要太快下结论。一次短按 J 后，事件记录已显示邮袋打开，自动化桌面工具的第一张截图却仍是上一帧；稍后的窗口截图和引擎画面才显示邮袋。另一次按 E 没有送信，是外部窗口抢走焦点触发暂停，E 实际关闭了暂停。

鼠标也出现过显示中心与当时按钮命中矩形相差数像素。调整窗口尺寸更新时机后，绘制与命中位置一致，100 毫秒点击和 J/E 短按实测成功。但没有单变量实验能证明旧偏移完全由这一处代码导致，不能把所有现象都包装成已定位的游戏缺陷。

可复用的检查顺序是：先看事件有没有到达、焦点在哪里、弹窗是否打开，再对齐截图时间与按钮矩形，最后修改输入逻辑。布局入口在 [main.gd](../game/scripts/main.gd) 的 `_fit_modal`，失焦处理在 `_notification`。

## 6. 手机尺寸和手机实玩，是两层验收

375×812 与 812×375 的实际桌面窗口已检查开场、邮袋、滚动和关闭位置，世界像素化也没有把文字一起变糊。这能发现小屏布局问题，却不能证明手机的触控取消、多指操作、浏览器工具栏、GPU 性能和声音都正常。

当前推荐手机横屏，但真实手机成功运行、触屏体验和音频听验仍待确认。174 项游戏断言覆盖规则、存档、全邮路控制器、布局与第三封光路；自动控制器约 35.2 秒的最短模拟路线不是首次玩家时长。完整返邮亭结尾有控制器测试，本轮没有重新手动走完这一段。测试范围见 [TESTING.md](../TESTING.md)。

## 7. gzip 文件能下载，不代表 WASM 能启动

Web 发布出现过一次实际故障：服务器没有按预期附加 `Content-Encoding: gzip`，压缩字节直接送进了 WebAssembly。错误中的 `1f 8b 08 00` 是关键线索，它对应 gzip 文件头。此前本地服务器补了正确响应头，因此本地成功并没有证明真实托管环境也正确。

现在显式请求 `index.wasm.gz`，由小型适配层检查实际字节，需要时解压，再核对解压后长度和 SHA-256，最后交给引擎。已经解压的响应也能识别，避免重复处理。资源地址使用相对路径，以支持 GitHub Pages 的项目子目录。实现见 [dusk-wasm-loader.js](dusk-wasm-loader.js)，验证见 [web-resources.test.mjs](../tests/web-resources.test.mjs)。

资源测试实际解压并编译官方 WASM，也覆盖损坏内容、错误页面与缺少解压能力的反馈。公开 Pages 的部署已成功，线上关键文件下载哈希与发布文件一致。不过当前测试用云浏览器在 WebGL2 能力预检就被阻止，没有进入游戏或尝试加载 WASM。资源层通过与浏览器图形启动通过，必须分别记录。

## 8. 把可恢复和许可一起放进工程

存档不能把“读取失败”默认为“新游戏”。坏 JSON 或非法状态应保留原文件，阻止自动覆盖；正常保存先写临时文件，再替换正式文件。源码与可运行 Web 包也按版本保存，公开提交保留可核对的资源清单。测试存档、机器路径和私人回执不进入公开工程。

分发时分别保留 Godot 的引擎及第三方声明、Noto 字体的完整 OFL 许可。实际字体许可没有指定具体保留名称，不能仅看到通用条款就臆造改名义务。原创游戏内容当前没有另行授予开源使用许可，公开可见不自动等于可任意再用，具体见 [LICENSE.md](../LICENSE.md)。

下一轮最有价值的工作，是在真实手机上完成一次不读攻略的邮路体验，记录首次迷路点、触控取消与帧时间，再据此改导航和性能。继续加场景细节之前，先确认玩家能看见光、理解反馈，并把信送到门口。
